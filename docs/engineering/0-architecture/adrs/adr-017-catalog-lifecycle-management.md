---

## Context

The Concilium catalog currently consists of:

```
config/catalogos/agis/
  insumos/            ~140 insumos por tipo (ADR-016 class annotations)
    equipamento.json
    mao_obra.json
    material.json
  cpus.json           11 CPUs calibrated against Lote 09/10 CE
  templates.json      EAP-base templates by obra type

config/producoes/
  ESCO-CARGA-1CAT-PROD-001.json   (and others)
```

**Nota arquitetural (Opção B, 2026-05-03):** O antigo `config/catalogos/agis/producoes.json`
era um índice desnormalizado que duplicava `valor_horario` dos artefatos completos em
`config/producoes/`. Esse índice foi removido. O conjunto de Producoes necessário a cada
catálogo é agora derivado dos campos `producao_id` das CPUs pelo `Runtime._load_producoes_from_cpus()`.
Isso elimina o risco de stale-data e torna o comportamento uniforme entre os catálogos
(agis, samples, test — nenhum tem índice próprio de Producoes).

ADR-007 established productivity as a first-class artifact with:
- Calibration origin (empirical > tabular)
- Confidence level (0–100%)
- Observation history (linked to real projects)
- Versioned evolution (PROD-001 → PROD-002 → PROD-003)

ADR-012 established catalog completeness as measurable and improvable, driven by authoritative sources (SICRO, SINAPI) and gap detection.

**What neither ADR addresses:** the **feedback loop** from live projects back into the catalog. Every project execution is an observation that can:

1. **Validate** existing values (confirm or challenge productivity, unit costs)
2. **Enrich** missing values (add productivity for a CPU that only had a tabular reference)
3. **Flag anomalies** (productivity 40% below catalog — equipment issue? data entry error? real degradation?)
4. **Propose updates** (new CPU variant, updated insumo price, revised class annotation)

Without this loop, the catalog ages — prices diverge from market, productivities reflect old equipment, class annotations remain guesses.

---

## Decision

We formalize a **catalog lifecycle model** with three phases:

```
PHASE 1: INTAKE    Project execution generates observations
PHASE 2: REVIEW    Observations reviewed for catalog relevance
PHASE 3: UPDATE    Approved observations update catalog artifacts
```

### D2 — Observation Intake (When and How)

Observations are generated at defined moments in the project lifecycle:

```
PROJECT LIFECYCLE → OBSERVATION TRIGGERS

S1 SCOPED:
  → ObservacaoCPUAusente if resolver-cpus returns NOCANDIDATE (ADR-002)

S2 PLANNED (after 06-consolidar):
  → No observations yet (plan only)

S4 APPROVED:
  → No observations yet (commitment)

POST-EXECUTION (Skill 12-decision-review):
  → ObservacaoProdutividade for each activity with actual data
  → ObservacaoCustoInsumo from finance reconciliation

MANUAL (field engineer, any time):
  → ObservacaoClasseRecurso when sharing behavior differs
  → ObservacaoCPUAusente for services not in catalog
```

**Intake mechanism:**

### D3 — Review Workflow

Observations accumulate in a **review queue** before touching the catalog:

```
Observation created
  ↓
Stored in: config/observacoes/{obra_id}/{tipo}/{timestamp}.json
  ↓
Anomaly check:
  if |delta_pct| > 30%:
    status = "ANOMALIA" → escalate to Senior Engineer immediately
  else:
    status = "PENDENTE" → enters normal review queue
  ↓
Batch review (weekly or per-project):
  Senior Engineer reviews pending observations
  For each:
    ├─ CONFIRMAR     → proceeds to catalog update proposal
    ├─ REJEITAR      → discarded (data quality issue, outlier)
    └─ INVESTIGAR    → flag for more data before deciding
  ↓
Catalog update proposal generated (D4)
```

### D4 — Update Proposals

Confirmed observations generate **update proposals** — not direct catalog changes:

```python
class PropostaAtualizacao(BaseModel):
    """
    A proposed change to a catalog artifact, pending approval.
    Never modifies catalog directly.
    """

    proposta_id: str              # UUID
    tipo_artefato: str            # "producao" | "insumo" | "cpu" | "cobertura"
    artefato_id: str              # Which artifact to update

    # Evidence
    observacoes: list[str]        # Observation IDs supporting this proposal
    n_obras_suporte: int          # How many projects support this change
    delta_medio_pct: float        # Average observed delta
    confianca_estimada: float     # Confidence in the new value

    # The proposed change
    campo: str                    # "valor_horario" | "custo_unitario" | "capacidade_cobertura"
    valor_atual: Any
    valor_proposto: Any

    # Justification
    justificativa: str
    fonte: str                    # "observacao_obra" | "reajuste_mercado" | "sicro_atualizado"

    # Governance
    status: Literal["PENDENTE", "APROVADA", "REJEITADA"]
    aprovador: Optional[str]
    data_aprovacao: Optional[date]
    nota_aprovacao: Optional[str]
```

### D5 — Approved Update Execution

When a proposal is approved, the update is applied with full audit trail:

```python
class CatalogUpdater:
    """Applies approved catalog proposals with versioning."""

    def apply_update(
        self,
        proposta: PropostaAtualizacao,
        aprovador: str,
        nota: str,
    ) -> CatalogUpdateResult:

        if proposta.tipo_artefato == "producao":
            return self._update_producao(proposta, aprovador)

        elif proposta.tipo_artefato == "insumo":
            return self._update_insumo(proposta, aprovador)

        elif proposta.tipo_artefato == "cpu":
            return self._update_cpu(proposta, aprovador)

    def _update_producao(self, proposta, aprovador):
        """
        Creates new Producao version (never overwrites existing).
        ADR-007: PROD-001 → PROD-002, old version preserved.
        """
        producao_atual = load_producao(proposta.artefato_id)

        nova_producao = producao_atual.model_copy(update={
            "id": f"{producao_atual.codigo}-PROD-{next_version()}",
            "valor_horario": proposta.valor_proposto,
            "origem": OrigemProducao(
                tipo="calibrado_contra_obra_real",
                fonte_id=proposta.observacoes[0],
                data_calibracao=date.today(),
            ),
            "qualidade": QualidadeProducao(
                confianca_pct=int(proposta.confianca_estimada * 100),
                quantidade_amostras=proposta.n_obras_suporte,
            ),
            "historico_observacoes": [
                *producao_atual.historico_observacoes,
                ObservacaoProducao(obra_id=obs_id, ...)
                for obs_id in proposta.observacoes
            ],
            "auditoria": AuditoriaProducao(
                modificado_por=aprovador,
                ultima_modificacao=datetime.now(),
                versao=next_version_str(),
            ),
        })

        save_producao(nova_producao)

        # CPU continues to reference old producao_id
        # until explicitly pointed to new version
        return CatalogUpdateResult(
            novo_artefato_id=nova_producao.id,
            versao_anterior=producao_atual.id,
            nota=f"Versão {nova_producao.auditoria.versao} criada. "
                 f"CPUs ainda referenciam {producao_atual.id}. "
                 f"Atualizar manualmente se desejado."
        )

    def _update_insumo(self, proposta, aprovador):
        """
        Insumos are updated in-place (no versioning) with change log.
        Price updates are time-stamped for historical audit.
        """
        insumo = load_insumo(proposta.artefato_id)
        insumo.custo_unitario = proposta.valor_proposto
        insumo.auditoria_custo.append({
            "data": date.today().isoformat(),
            "custo_anterior": proposta.valor_atual,
            "custo_novo": proposta.valor_proposto,
            "aprovador": aprovador,
            "justificativa": nota,
        })
        save_insumo(insumo)
```

### D6 — Catalog Health Extended (ADR-012 Extension)

ADR-012 `CatalogHealthReport` gains staleness metrics:

class CatalogHealthReport(BaseModel):
    # ... existing ADR-012 fields ...

    # Staleness (new in ADR-017)
    producoes_desatualizadas: int   # Last calibrated > 12 months ago
    insumos_preco_desatualizado: int  # Last price update > 6 months ago

    producoes_sem_obra_real: int    # origen = "tabela_referencia" (no empirical data)
    insumos_sem_classe: int         # Missing ADR-016 annotation
    cpus_sem_producao: int          # CPU without producao_id

    # Activity
    ultima_calibracao: date         # Most recent observation processed
    obras_contribuindo: int         # Projects that generated observations

    # Overall health
    status_dados: Literal["ATUALIZADO", "DEFASADO", "CRITICO"]
    # ATUALIZADO:  producoes_desatualizadas = 0, observacoes_pendentes < 5
    # DEFASADO:    some stale, queue building up
    # CRITICO:     major portions stale or queue > 20

## Summary

**Decision:** The catalog is a living artifact, not a static configuration file. Every project execution is an opportunity to validate, challenge, or enrich catalog values.

```
PROJECT EXECUTION
  ↓
Observations (produtividade, custo, classe, ausência)
  ↓
Review queue (Senior Engineer, weekly)
  ↓
Update proposals (if thresholds met)
  ↓
Approved proposals → versioned catalog updates
  ↓
Health report tracks staleness + queue depth
```

**Consequence:**
- Catalog accuracy improves with project volume, not despite it
- No observation directly modifies catalog (review gate always present)
- Every catalog value is traceable to its evidence (ADR-007 audit trail)
- Stale values are visible and actionable (ADR-012 health report extended)
- Class annotations (ADR-016) are empirically validated, not permanently assumed
